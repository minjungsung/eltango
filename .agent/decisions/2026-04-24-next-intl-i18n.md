# Internationalization via `next-intl` with `[locale]` routing

**Date:** 2026-04-24
**Status:** accepted

## Context

The landing page needed to serve both Korean (primary audience: local Seoul tango students) and English (international dancers visiting Buenos Aires or from abroad). The app was a single-locale Next.js 14 App Router project with all Korean copy hard-coded in `components/sections.tsx`.

## Decision

Adopt **`next-intl`** with a `[locale]` segment in the App Router (`app/[locale]/layout.tsx`, `app/[locale]/page.tsx`) and a `middleware.ts` that detects the browser's `Accept-Language` header and routes accordingly. Translations live in `messages/{en,ko}.json`. The `components/language-switcher.tsx` toggle navigates between `/en` and `/ko`.

## Alternatives considered

- **`react-i18next`**: more popular but awkward with App Router server components.
- **`@lingui/js`**: excellent DX but adds a build step (macro compilation).
- **Hard-code both languages with a manual toggle**: reject — doesn't scale past 2 languages and duplicates all JSX.
- **Route-less `Accept-Language` detection without `[locale]`**: reject — hurts shareable URLs and SEO per language.

## Consequences

- Adding a new language is: add `messages/<code>.json` + list it in `i18n/routing.ts`.
- URLs are now `/en/...` and `/ko/...` — any external link to the old root needs a redirect (middleware handles default).
- All user-visible strings must go through `useTranslations()` / `getTranslations()` — raw JSX text is a regression.
- Per-locale metadata (OG, lang attribute) is wired via the `[locale]/layout.tsx`; currently generic, tracked in ROADMAP **Later**.
